# Proxmox VE 8 to 9 Major Upgrade

Official procedure: <https://pve.proxmox.com/wiki/Upgrade_from_8_to_9>.

This runbook supports only **PVE 8 / Debian bookworm → PVE 9 / Debian trixie**.
Run one host at a time. `PVE_HOST` must equal exactly `pve-1` or `pve-2`.
The Taskfile passes `--limit`; Ansible independently refuses any run that does
not resolve to that one inventory host.

## Host-specific outage facts

- `pve-1` is the NAS/storage host. It hosts VM `101` and CT `100`, `104`,
  `105`, and `106`.
- `pve-2` hosts VMs `100`–`103`, carrying Kubernetes control plane/workers.
  It is a one-node Proxmox cluster, **not** a standalone host.
- Both hosts currently have a `pve8to9` blocker: the `systemd-boot`
  meta-package, plus a removable-GRUB warning. `pve-1` additionally has CT100
  legacy `lxc.cgroup` configuration and NVIDIA DKMS; `pve-2` has settings in
  `/etc/sysctl.conf`.

Automation reports and fails on those conditions. It never removes
`systemd-boot`, repairs GRUB, rewrites CT100 cgroups, alters NVIDIA DKMS,
migrates sysctl settings, upgrades ZFS pool features, or stops/starts guests.
Resolve every blocker manually according to the official guide before retrying.

## Routine package maintenance

Routine maintenance is serial across `[proxmox]`; no reboot by default:

```bash
task update:proxmox-packages-no-reboot
```

Use only during an approved maintenance window, for one exact host, when a
required reboot is acceptable:

```bash
task update:proxmox-packages-with-reboot PVE_HOST=pve-1
```

## Required evidence before major upgrade

1. Record verified, restorable backup evidence for every guest and host data.
   For `pve-1`, include NAS/storage recovery. For `pve-2`, include Kubernetes
   control-plane/worker recovery and the one-node cluster configuration.
2. Schedule and communicate the host outage. Shut down/migrate guests manually
   if required; this automation does not do so.
3. Resolve all `pve8to9 --full` failures and the known boot/LXC/DKMS/sysctl
   blockers manually. Do not proceed on warnings you do not understand.

`BACKUP_VERIFIED=true` and `OUTAGE_ACKNOWLEDGED=true` are explicit operator
acknowledgements, not proof generated by Ansible.

## Exact command sequence

Replace `<host>` with `pve-1` or `pve-2`. Complete the entire sequence for one
host before beginning the other.

```bash
# Read-only: source release, pve8to9, dpkg, apt sources, storage, ZFS health,
# guest inventory, and known blockers. Requires documented acknowledgement.
task proxmox:major:preflight PVE_HOST=<host> BACKUP_VERIFIED=true OUTAGE_ACKNOWLEDGED=true

# Mutating: update current PVE 8, rerun checker, make dated source backups,
# change only allowlisted Debian/PVE sources, simulate, then dist-upgrade.
# Does not reboot.
task proxmox:major:upgrade PVE_HOST=<host> BACKUP_VERIFIED=true OUTAGE_ACKNOWLEDGED=true

# Use only after a failure after source rendering. Requires exact canonical trixie
# sources and clean manual dpkg recovery; it never restores bookworm sources.
task proxmox:major:resume PVE_HOST=<host> BACKUP_VERIFIED=true OUTAGE_ACKNOWLEDGED=true RESUME_CONFIRMED=true

# Separate prompt-gated reboot. It waits for SSH and proves boot ID changed.
task proxmox:major:reboot PVE_HOST=<host> OUTAGE_ACKNOWLEDGED=true REBOOT_CONFIRMED=true

# Read-only target validation: PVE/Debian major, kernel, dpkg, services,
# storage, and guest inventory.
task proxmox:major:verify PVE_HOST=<host>
```

The upgrade phase first updates current PVE 8 packages. It refuses source
migration if that leaves a reboot pending or `pve8to9 --full` non-clean. It
also refuses an already-target or partially trixie-migrated source state before
any apt mutation. It then backs up only known apt source files and renders
`/etc/apt/sources.list` exactly with official trixie main, updates, and
security repositories (`main contrib non-free non-free-firmware`). It disables
an existing `debian.sources` and legacy PVE lists, then leaves exactly one
canonical `pve-no-subscription` channel. It never does broad codename
replacement.

## Recovery boundary

There is **no supported in-place downgrade** from PVE 9 to PVE 8. Recovery is
restore/rebuild from verified backups and the recorded pre-upgrade state; do
not treat the dated apt-source copies as a rollback mechanism.
